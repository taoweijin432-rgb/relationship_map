# 入图时人物关系预计算与边字段

版本 v1.3 ｜2026-11-06 ｜模型 uuid-relations-v5 ｜架构 v0.22

## 2026-11-11 可选同校前提

用户最新说明已由主方案v0.44落实。same_major查询可勾选要求两人已有same_school关系，并对多跳各段应用。学校及专业可来自不同教育行。前端新查询默认勾选，API默认false。v0.43严格同教育行及新增same_school_major边提案退役。当前图继续消费既有四类物化人物边，前提在图查询中按人物对取交集。

人物姓名不写图，person 保留来源和业务编号，显示时回 SQL，见 [隐私边界](graph-privacy.md)。

用户明确要求：在数据入图阶段计算并保存人物之间的关系。目标因此由只有经历事实的 uuid-facts-v1，调整为“经历事实＋预计算人物关系”。关系计算仍由图中的经历事实和 nGQL 完成；Python 负责批次编排、结果写入和对账，SQL 提供冻结的来源详情。不是把 SQL 提前计算结果后将图用作装饰。

## 1 两层图结构

| 层 | 边 | 来源 |
| --- | --- | --- |
| 经历事实 | worked_at、studied_at、studied_major | 原人物、经历、有效归一映射与标准实体；事实 Rank=graph_edge_mapping.id |
| 人物关系 | same_company、company_overlap、same_school、same_major | 导入时从事实边计算得到；双方都是 person 节点 |

物理 DDL 为 [基础节点／经历边](../infra/nebula/schema/uuid-facts-v3.ngql) 加 [人物关系边](../infra/nebula/schema/person-relations-v3.ngql)，按顺序在全新空间执行。基础文件保持不变以保留 v1 验收；新投影的 projection_meta.schema_version 必须写 uuid-relations-v5。完整结构与来源见 [图 DDL](graph-ddl.md)。

不生成任意“认识”“可引荐”“好友”边；这些不能由共同经历证明。相同职位不自动生成人物关系；同专业须指向同一标准专业 UUID，不按原文相似程度判断，母子公司不当同公司。间接连接链在查询时沿已计算的直接关系遍历，不预先存所有两跳人物对。

## 2 四种关系的计算定义

| 人物边 | 入图时成立条件 | 时间规则 |
| --- | --- | --- |
| same_company | 两个不同人物的有效 worked_at 指向同一公司 UUID | 不要求同期；日期未知仍成立 |
| company_overlap | same_company 的一对经历在基准月规则下存在月份交集 | 双方开始与有效结束已知、各自区间有效；交集起点不晚于终点 |
| same_school | 两个不同人物的有效 studied_at 指向同一学校 UUID | 不要求教育日期，不推断同届或实际认识 |
| same_major | 两个不同人物的有效 studied_major 指向同一专业 UUID | 不要求同校、同届或教育日期；不表示同职位或实际认识 |

company_overlap 是 same_company 的子集。同一对经历满足同期时，两类边各保留一条，分别支持两类查询；列表按人物去重，不能把两类边算成两个人或累加成评分。同校与任职也可以同时成立。

same_major 以归一后的专业 UUID 精确相等为依据，不按专业显示名、学科大类或岗位文字猜测。两人可能来自不同学校，也可能缺少学校映射，均不妨碍已确认专业形成关系。如果后续增加“同校同专业”组合能力，还须核对每个人的学校和专业属于同一条原教育经历；不能把两条独立人物关系直接当作同一段教育证据。

一条人物关系边对应“人物对＋关系类型＋共同实体＋左经历 Rank＋右经历 Rank”这一对证据，不把多个共同实体或多次任职压成一条无从解释的摘要边。多次经历保留多个证据边；候选和列表去重人物，证据面板分页展示这些边。不同原经历主键即使内容相似也不由系统擅自合并。

## 3 人物关系边的完整图键

两个人物 VID 以 ASCII 字节顺序比较，较小者为 src、较大者为 dst，排除 src=dst。业务关系无方向，但物理只写一条方向，不额外双写反向边。查询从任意人物使用双向遍历；读到反向时，证据字段仍按原存储 src／dst 解释，不按当前查询中心交换含义。相关语法见官方 [GO 的方向控制](https://docs.nebula-graph.io/3.8.0/3.ngql-guide/7.general-query-statements/3.go/)。

| 图键 | 生成规则 | 注意 |
| --- | --- | --- |
| src VID | 人物对中较小 VID | 必须为 person；这只是存储排序，不是主次或关系方向 |
| dst VID | 人物对中较大 VID | 与 src 不同；不进行同名或跨库身份猜测 |
| type | same_company／company_overlap／same_school／same_major | 项目规则固定，不能用任意字符串表示已认识 |
| relation Rank | 在同类型、src、dst 内，按 (entity_vid,left_fact_rank,right_fact_rank) 排序，依次编号 1..N | 是当前快照局部证据序号，不是源表主键，不保证跨版本不变 |

人物关系 Rank 与经历事实 Rank 是两个概念。不能拿人物关系 Rank=1 去查 graph_edge_mapping.id=1。跨版本定位关系证据使用模型／投影版本＋人物对＋类型＋共同实体＋双方事实 Rank；即使事实 Rank 不变，目标实体或人物归属改变也会改变完整关系键。

## 4 每个边属性的用途、来源和空值

same_company、same_school 和 same_major 各有以下 3 个属性；company_overlap 包含这 3 个属性以及后面的 2 个交集属性。全部 NOT NULL，不设置默认值。它们来自图内计算结果，不是上游 MySQL 新增同名列的要求。

| 属性 | 图类型 | 用途 | 图中依据及 MySQL 追溯 | 空值与校验 |
| --- | --- | --- | --- | --- |
| entity_vid | STRING | 解释共同公司／学校／专业，限制共同实体 | 两条事实边共同终点；追溯至双方 graph_edge_mapping.standard_entity_id 和 graph_company_entity.id／graph_school_entity.id／graph_major_entity.id | 非空；必须同实体且类型匹配；不按名称相等生成 |
| left_fact_rank | INT64 | 定位存储 src 的那条经历 | src→entity 的 worked_at／studied_at／studied_major Rank；对应 graph_edge_mapping.id，再定位原工作／教育行 | 正数；必须确有该完整事实边、且归属 src |
| right_fact_rank | INT64 | 定位存储 dst 的那条经历 | dst→entity 的 worked_at／studied_at／studied_major Rank；对应 graph_edge_mapping.id | 正数；必须确有该完整事实边、且归属 dst |
| overlap_start_month | INT32 | company_overlap 交集开始，用于时段筛选 | nGQL 取两条 worked_at.start_month 的较大值；原始依据是两条工作行 start_date | 仅同期边存在；必须为合法月份，不得 NULL |
| overlap_end_month | INT32 | company_overlap 交集结束，用于时段筛选 | nGQL 取双方有效结束月的较小值；有效结束来自原 end_date 或当前任职时的明确基准月 | 仅同期边存在；必须不早于开始，不得 NULL |

same_company／same_school／same_major 不存 NULL 交集字段，也不存虚构同期状态。需要展示原始任期时按两个事实 Rank 从冻结 SQL 回查；图上的交集不替代原日期。

## 5 时间计算和查询筛选

当前任职的空结束月使用发布基准月解释；非当前缺结束月保持未知。必须先验证双方开始不晚于各自有效结束，再计算 max(开始) 与 min(有效结束)。NULL 不补 0，不以查询执行时的系统月份改变已发布关系。

当前任职跨月后，company_overlap 的结束月可能变化，新的数据基准月必须重算并发布新版本，不能只改控制节点日期。图／SQL／清单及派生边使用同一基准月。对未来月份没有快照依据的查询需限制或要求新版本，不把旧交集无限外推。

查询选定时间窗口后，在图中把每条预计算交集与窗口求交、计算单条经历对月份数；不在 SQL 重算人物关系，不累加重叠证据制造阈值。没有 company_overlap 的未知日期经历不因此丢掉 same_company；同校和同专业仍不要求日期。

## 6 入库／发布阶段的顺序

1. 冻结原人物、经历、归一、标准实体与边槽位，预检身份、引用、有效状态、日期和发布范围。
2. 新建独立空间，写四类节点和三类事实边；控制节点为 staging。
3. 回读事实对账后，按公司／学校／专业分批，从图内计算不同人物的经历对；同期由 nGQL 判断并输出交集。
4. 校验并按证据键排序分配人物关系 Rank，分批写入四类人物边。驱动不使用 Python overlap 或 SQL 重新认定关系。
5. 回读派生边，核对总数、重复键、双方事实引用、独立人工预期和各关系类型完成情况。
6. 事实与人物关系均完整通过后，控制节点才可 ready，并输出不可变成对清单。任一阶段中断／超过预算均不能作为完整图发布。

人物直接查询优先读取 same_company／company_overlap／same_school／same_major。一位中间人物使用这些边做最多 2 条业务边遍历，并返回每段的实体和两个事实 Rank。底层事实边保留用于证据和后续重新构建；不会因为有派生边就丢掉事实层。

## 7 修正、失效与重算

原人物、经历、名称映射或实体失效，人物归属／标准目标改变，任期或当前状态纠正，都可能改变派生边。新快照先重建正确事实，再生成全部对应人物关系，验证失效证据的关系边消失；其他有效证据仍可使同一对人物保留关系。不能只改事实边却留下旧人物边，也不能删除一条证据就把该人物对的全部关系删掉。

当前选择完整新空间构建，旧空间保留回退。未来若做增量，应根据改动前后的实体和人物定位影响范围，删除旧派生证据键并重算，再按发布契约切换；本轮不实现生产增量、在线多边事务或旧边自动清理。

## 8 规模与完整性约束

人物对预计算会放大数据。一个公司有 n 位不同人物、每人一条任职，同公司无向人物对为 n×(n−1)/2；1 万人约 4999.5 万对。每人多条任职时证据边数是不同人物各经历数的交叉乘积之和，还可能额外生成同期边。同校、同专业同样需要估算，热门专业可能覆盖更多人物。这是结构性的规模问题，不能用 6 人样例证明全量可行。

构建前统计每实体人数／经历数、预计派生边数和热门实体分布；设定内存、返回行数、RPC、写入和构建时间预算。分页遍历、分批写入和断点方案需在正式构建器落实，LIMIT 不是计算规模上限。只算前 N 人、静默丢弃热门实体、取 Top K 或在预算耗尽时仍 ready 都不满足“全部已确认关系预计算”。

若代表性数据下全量关系边不能接受，应提交调整方案及完整性影响再决定，例如只预计算同期、按业务时间窗分层或保留部分事实遍历；本轮不擅自把用户要求退回仅查询时计算。生产容量、索引和最终计算调度仍待真实分布验证。

## 9 本轮交付边界

本轮确定 DDL 与规则，并用独立临时空间演示“写事实→图计算→写人物边→读取关系／证据”，不迁移旧 API、既有 MySQL／图或清单，不访问 Supabase。验证脚本是限定小样例演练，不能作为百万级构建器，也没有实施生产增量。

执行入口与证据见 [同专业及人物关系预计算验证](person-relations-v3-validation.md)。历史 uuid-facts-v1 的 10 项检查只证明事实层；v2 的 14／10 条结果只涵盖三类人物边，均不能作为新增同专业的验收。同专业人工基准仍为 v3；历史 v4 已验证人物姓名不入图；当前 v5 增加业务属性并回归隐私与关系，见 [业务字段验证](graph-business-fields-validation.md)。历史隐私结果，见 [隐私验证](graph-privacy-validation.md)。
