# 学校曾用名候选修复

版本v0.60，2026年11月16日。本次修复基于提测代码`3a9c48f`／`qa-20261113-02`，交付状态为本地实现及原生验证完成，测试服务器上线待执行。

用户反馈输入“广东医学院”和“浙江科技学院”时学校候选为空，输入标准名可以选择对应学校。两个名称分别应定位到`school:41`广东医科大学和`school:73`浙江科技大学。

## 原因及处理

实体采集使用完整物理行，冻结的`entity-source.json`已经包含上游学校`former_names`。真实构建的`real_contract`通过显式字段白名单生成逻辑快照，旧白名单未包含该字段。数字SQL读模型根据图节点装配学校，仅写入标准名，`demo_entity.aliases`为空数组，`demo_entity_alias`没有记录。候选API已具有标准名前缀与别名前缀检索逻辑。

`scripts/build_real_graph.py`将真实读取契约标识更新为`real-split-mysql-v2`，冻结输入中学校包含`former_names`时，显式将其纳入逻辑快照和来源摘要。历史冻结输入整体缺少该字段时继续按空别名处理，契约已包含字段的输入须逐行符合契约。曾用名变化会进入新的来源摘要及数据版本，由现行夜间发布处理。

`numeric_read_model.py`以已发布学校节点的原整数ID定位源行，读取`former_names`后同时写入实体的别名数组及候选别名索引。支持SQL NULL、JSON null、JSON字符串数组及已解码数组。条目按首尾空白清理、去空、去重并排除标准名。同一曾用名被上游登记给多个实体时，各自保留对应关系，候选继续按标准实体返回。

已删除、已合并及其他未进入发布投影的学校，其曾用名随所属实体过滤。非法JSON、对象和非字符串数组项会使候选准备失败，现有发布流程按错误处理并保留可恢复记录。曾用名只进入配套SQL读模型，实体ID来自上游权威表。

## 服务器生效步骤

上线包含两个运行文件，分别为`backend/src/relationship_query/infrastructure/numeric_read_model.py`和`scripts/build_real_graph.py`。代码按后续Git提交及提测标签管理，既有`qa-20261113-02`用于追溯原提测版本。

更新构建代码后，需要重新读取上游、准备并完整发布候选，随后由查询服务加载该完整新发布。现行夜间任务每天04:30自动完成采集、构建、核验和切换，最大窗口90分钟。构建使用冻结输入时，曾用名必须存在于原始`entity-source.json`，从旧逻辑快照直接构建无法恢复被筛掉的字段。

服务器验收应记录届时实际版本，核对`person_display=mysql-live`，再以两个曾用名和标准名验证相同学校ID及相同筛选结果。原已发布SQLite由完整版本发布流程替换，发布摘要及查询启动校验沿用现有机制。

本轮验证范围为本机封存真实数据、独立图及指定浏览器操作。测试服务器修复激活及其当前最新来源结果需在上线后核验。
