## 信息需求及缺失影响

“查询所必需”是正确定位人物、构建共同经历或回查证据的基础；“仅某项能力需要”表示缺少时应限制相应能力；“待上游确认”表示现阶段不能从原型推定生产规则。

| 信息 | 分类 | 查询用途 | 缺失影响或待确认内容 |
| --- | --- | --- | --- |
| 稳定人物标识及其生命周期 | 查询所必需 | 两个入口引用同一个人，分页去重 | 无法可靠关联经历；姓名不能代替人物键 |
| 专家／简历来源系统与来源人物引用 | 查询所必需 | 来源过滤、回查人物、解释双来源 | 不能按库筛选或回查；需说明来源人物键不是经历键 |
| 跨库人物与统一人物的关联结果 | 查询所必需 | 上游确认同一人后合并来源 | 未提供关联时只能按独立来源人物展示，不由查询系统猜测 |
| 标准实体标识、类型和名称 | 查询所必需 | 判断同公司、同校及标准职位筛选 | 同名文本不能直接认定同一实体；公司学校类型分别处理 |
| 每条经历关联的标准实体结果 | 查询所必需 | 人物→经历→公司／学校 | 只有实体名称词典、没有经历映射时，仍无法构建人物关系 |
| 一次工作经历中的人物与公司关联 | 查询所必需 | 人物任职事实、同公司及证据定位 | 不允许只有互不关联的人物表和公司词典 |
| 职位及其所属工作经历 | 仅某项能力需要 | “在 A 公司担任 B 职位”的同条经历约束 | 无职位时仍可查公司；有职位时不能从人物公司集合和职位集合拼出未经证实的履历 |
| 稳定经历键和来源定位 | 查询所必需 | 区分重复任职、查看双方证据 | 无法解释、纠正或准确失效某次经历 |
| 人物及经历的有效状态 | 查询所必需 | 排除已失效记录 | 无法知道哪些关系仍有效；具体状态枚举和删除机制待确认 |
| 工作开始月、结束月、当前任职标记 | 仅某项能力需要 | 同期判断和任职时间筛选 | 不完整时间仍可查同公司；不能凭此认定同期 |
| 教育时间 | 仅某项能力需要 | 后续如有需要再支持同期教育 | 当前同校不依赖教育时间，也不推断同期 |
| 实体别名 | 仅某项能力需要 | 通过简称／旧名称定位标准实体 | 仍可按标准名称／ID 查询；歧义别名不自动决定归属 |
| 人物显示摘要、城市、脱敏名称 | 仅某项能力需要 | 列表、详情和人物定位体验 | 原型有展示字段，但不能据此要求上游照搬字段；可评估受控回查 |
| 业务更新时间、扫描时间、版本 | 待上游确认 | 后续增量与迟到纠正 | 哪个时间表达业务变化、是否回填、是否可靠单调推进 |
| 逻辑删除、物理删除、恢复 | 待上游确认 | 失效传导与补偿 | 标记、事件还是快照差异；是否有完整删除记录 |
| 实体合并、拆分和别名纠正 | 待上游确认 | 更换归一结果后重算相关关系 | 旧 ID 是否重定向，哪些经历受影响，如何通知查询侧 |
| 人物关联修正或拆分结果 | 待上游确认 | 采用上游新映射更新经历归属 | 稳定人物键是否保留、重定向或替换；查询侧不执行身份识别 |
| 完成批次、交付形式和快照范围 | 待上游确认 | 判断文件／视图是否完整可用 | 表／只读视图／文件、全量或增量、完成标记、范围和版本 |

这些分类不代表允许把缺少基础标识的数据直接发布。若某类信息确实无法提供，需要先明确缩小哪些查询能力，再调整架构。

## 时间和空值口径

- 原型逻辑月份用 YYYYMM，精度为月，首尾月份计入交集。2020.12—2021.01 计 2 个月；同一月份计 1 个月。
- 当前任职且没有结束月时，以数据集基准月份作为本次计算上界，不回写虚假的结束时间。
- 结束月为空而当前任职未确认时，保持未知，不能当作当前任职。当前任职开始月晚于批次基准月，属于逻辑矛盾。
- 双方任职同期需要可确定的双方区间。某条经历时间不完整，不阻止同公司查询，也不会被自动补全日期。
- 任职筛选只填起始月时，要求已知有效结束月不早于它；只填结束月时，要求已知开始月不晚于它；两端都填时，两个条件须由同一经历满足。不能把单侧筛选命中解释为已经知道完整任期。
- 教育日期缺失时，同校仅表示关联同一标准学校。样例的 is_current 专指工作“当前任职”，不用于表达在读。
- 上游若只有年份、季度、文本“至今”或零日期，需要明确精度与转换规则；本轮不预设物理字段解析和补月规则。

## 虚构逻辑样例和只读预检

配套文件是 `examples/logical-dataset.json`，包含 14 名人物、10 个实体、29 条经历，其中包含失效记录、同名人物、双来源和不完整任期。它是查询原型的逻辑输入示意，不要求同事照此输出文件，更不代表正式接口或 DDL。

原型输入有 version、reference_month、people、entities、facts。现有字段格式由 Pydantic 模型校验；人物与实体采用可区分的字符串 ID，经历还保留来源系统和来源记录键。图节点及生成的边 ID 冲突时会阻断，预检不会自动加前缀。正式适配时应从上游标识建立明确映射，不把不同来源数字 ID 直接当成全局键。

在项目根目录运行：

```bash
backend/.venv/bin/python -m relationship_query.cli validate-dataset \
  --input docs/examples/logical-dataset.json
```

此命令不读取演示数据库、不建目录、不建表、不导入或修改输入文件。它只输出 JSON 报告：report_version、data_mode、data_version、valid、counts、errors、warnings。

- 每条问题提供 code、path、message，以及可用的 record_id / related_ids。path 使用 `/facts/0/person_id` 这样的定位方式；`/` 表示文件或根位置。
- counts 是文件中的记录数，包含失效记录，不是线上有效人物统计。
- errors 阻止导入：结构／日期错误、重复 ID、悬空或类型错误引用、来源未关联、空标识等。退出码为 1。
- warnings 用于人工核对：不完整任期、疑似重复经历、同类型名称／别名歧义。不会自动去重、合并、纠正或补日期；只有提示时退出码为 0。
- 文件不可读、非 UTF-8 或 JSON 错误也返回 JSON 问题报告及退出码 1；命令用法错误由参数解析器报告并返回 2。
- 结构不满足模型时先报告结构错误；修复后再检查跨记录引用。检查通过不证明上游抽取完整、归一准确或数据可上线。

配套样例预期 valid=true，并有 4 条提示：3 条任职时间不完整、1 条疑似重复经历。别名歧义使用独立测试构造，不污染此样例。逻辑空快照允许表达“空集合”，但必须另外核实上游完成标记和抽取范围，不能把无数据当作交付完成。

初始化和只读预检复用相同校验入口。错误会在建表／写入之前阻断；现有数据不会因预检或失败的校验被重置。

## 正式接入步骤与进入条件

| 步骤 | 所需材料／验证 | 进入下一步的条件 |
| --- | --- | --- |
| 语义与字段映射评审 | 最新结构、字段含义、样本、状态和来源键 | 必需信息能定位；未定项有明确影响范围 |
| 代表性样本预检 | 映射为逻辑输入后的样本及问题报告 | 阻断错误解决；提示有上游或业务结论 |
| 查询结果核对 | 人工预期人物与双方经历证据 | 覆盖两入口和已确认关系规则，不能只验证接口成功 |
| 容量与执行计划评估 | 真实经历量、实体规模分布、负载、部署条件 | 决定读模型、SQL／图分工、索引、缓存和资源 |
| 更新与纠正联调 | 删除／恢复／映射修正样例，批次和重放方式 | 变化能影响正确人物范围，进度与一致性可验证 |
| 灰度与验收 | 代表性负载、权限、观测和恢复报告 | 按已确认指标通过，不以本机 SQLite 结果代替 |

当前缺失物理字段、真实数据质量、删除事件可靠性、归一纠正传播和生产容量证据。因此不冻结生产 DDL、评分权重或部署规格。
