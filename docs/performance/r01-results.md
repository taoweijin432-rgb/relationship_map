# R01 模拟规模与查询诊断

日期：2026-11-03。实现版本 v0.8，全部使用固定种子的虚构数据；没有接入专家库或简历库，没有安装其他数据库。

## 结果与边界

已完成 1 万／10 万人、21 个场景、baseline／current 两种策略的接口实验，共 84 组，每组首次观测一次并预热重复 7 次，总计 672 次接口请求。所有请求成功完成，没有触发观察工具的 SQL 或子进程外部超时。另在两档数据上各运行普通人物、热门公司、普通公司三个浏览器场景，每个三轮，共 18 组交互观察。

最主要的改进是：热门／长履历路径从“SQL 执行预算耗尽，尚未核查中间人物”变成在相同业务预算下核实并返回 10 条间接链。它仍然受候选数、链数与证据展示上限约束，返回明确原因，不代表完整的全局路径集合。

发现但未在本轮改变契约的问题：长履历两人对比产生 13,804 条完整证据，响应约 18.25 MB。这不随数据库从 1 万增长至 10 万而消失，不能用较短的服务耗时掩盖传输和浏览器风险。后续应评估服务端证据分页、摘要及时间轴聚合；本轮未偷偷裁剪证据，也未测量该极端对比的浏览器渲染耗时。

这些数字是本机 SQLite 单次及顺序重复观察，不是并发压测、生产 SLA 或百万级容量证明。

## 数据与方法

| 数据库大小 | 13,561,856 字节 | 133,697,536 字节 |

数据配置为 scale-v1，种子 42，基准月 202611。包含热门实体、普通实体、少量长履历、重复来源、双来源人物、日期不完整、当前任职、失效记录及稳定手工边界人物。数据分布是刻意构造的压力情形，不是对公司数据分布的估计。

数据按 1000 人一批生成并复用现有共享校验，批量写入新 SQLite 文件，结束时建立统计信息 ANALYZE。不会把全量模拟数据一次放入 Python 内存，也不修改默认演示库。版本、逻辑内容摘要、索引、SQLite 参数、Python 和系统环境均在原始报告中记录。

每个场景在一个独立子进程中运行 ASGI TestClient，经过真实路由、服务和响应序列化，排除子进程启动、生成数据与执行计划收集时间。首次观测不是清空操作系统缓存的冷启动。P95 采用最近秩法，7 个预热样本下接近最大值，只供定位问题。顺序固定为 baseline 再 current，没有随机化或清空系统缓存，因此相同 SQL 的小幅耗时差异不能视作优化收益。

默认每次观察的非路径 SQL 有 2 秒／约 2000 万 VM 步保护，单场景子进程有 30 秒外部保护；触发时会明确报告，不计为正常空结果。路径保留原有 1500 毫秒、约 50 万 VM 步、5 万经历对等业务预算，观察器不覆盖路径 progress handler。所有请求成功，以上外部保护未触发。

阶段耗时是嵌套 inclusive wall time，不可相加当作总耗时；SQL cursor 执行时间不包含全部 fetch，近似 VM 指令数也不是扫描行数。深游标场景构造 90% 位置的合法游标，只观察该页，不包含前面各页的成本。

## 路径优化依据

baseline 是冻结在 benchmark 模块中的 v0.7 候选 SQL：从端点经历 JOIN 全部共同实体经历，DISTINCT 后排序。执行计划显示热门场景需要临时去重结构，即使最终只要少量候选，也先消耗了大量 VM 预算。在两档数据各 8 个热门路径样本中，baseline 都因 sql_limit 停止，中间人物核查数为 0；直接证据仍保留并标记受限。

current 增加最多 513 条索引记录的展开量探测：稀疏实体继续使用原 JOIN 方式；关联记录超过 512 时改为按人物 ID 顺序配合 EXISTS，找到候选上限后停止。两种策略保留同一关系对谓词、去重、来源过滤及排序。没有提高原有路径预算，没有新增索引、表或缓存；阈值是本地 SQLite 的临时选择，不能照搬为生产参数。

| 10 万人场景 | baseline | current |
| --- | --- | --- |
| 热门路径间接链数 | 0 | 10 |
| 核查中间人物数 | 0 | 11，额外一条确认展示截断 |
| 停止原因 | SQL 预算及证据展示上限 | 候选、路径及证据展示上限 |
| 热门路径预热 P50 | 7.543 毫秒 | 8.635 毫秒 |
| 长履历路径预热 P50 | 8.255 毫秒 | 16.256 毫秒 |

current 装配了更多有效路径和更大响应，总耗时有所上升，收益是相同预算下提供可用证据，而非宣称所有查询更快。稀疏场景多一次有界探测，也有小额开销。遇到严格时间窗、低命中率或其他数据分布，仍可能触发预算；不能保证该策略总是最优。

完整查询响应的 before／after 语义摘要均一致。受限路径只比较共同返回链的证据，不能把不完整结果冒充全量。另有 400 人独立日历月份集合核对全部候选集合，2000 人多种范围／来源／端点核对稳定前缀，以及原有 500 人独立路径与列表差分继续回归。

## 浏览器观察

Chrome 156.0.8078.80、本机 Vite 开发服务、1600×1000、单 Worker。每档 9 组交互，无页面异常、无接口失败。两档独立库及默认演示库的内容摘要保持不变。

| 数据规模 | 普通导航到列表与图稳定，三轮毫秒 | 热门公司选择到图稳定，三轮毫秒 | 普通公司选择到图稳定，三轮毫秒 |
| --- | --- | --- | --- |
| 1 万 | 510／296／298 | 373／376／363 | 402／379／376 |
| 10 万 | 550／312／313 | 381／373／372 | 398／386／390 |

选择到图稳定包括现有 250 毫秒查询防抖及两个绘制帧；标准名称远程定位另约 0.36–0.38 秒，包含选择器的输入等待。首次导航有约 94–102 毫秒的浏览器长任务，其余这些样本未记录超过 50 毫秒的长任务。没有证明持续帧率或将长任务归因到某个具体函数。

图始终限制在最多 100 节点、200 边，10 万是数据库人物规模，不是画布节点数量。以上不是生产构建、慢网络或低配办公设备结论。浏览器细节见 [1 万人](r01-browser-10000.json) 和 [10 万人](r01-browser-100000.json)。

## 复现

在项目根目录使用已有虚拟环境；报告目录必须是新目录：

```bash
backend/.venv/bin/python scripts/benchmark_scale.py \
  --output data/benchmarks/my-run --sizes 10000 100000 \
  --repeats 7 --seed 42 --strategy both --keep-databases

# 先停止普通开发服务。浏览器脚本只接受上述报告登记的 scale-v1 虚构库。
backend/.venv/bin/python scripts/benchmark_browser.py \
  --database data/benchmarks/my-run/scale-10000.sqlite \
  --output data/benchmarks/my-run/browser-10000.json

backend/.venv/bin/python scripts/benchmark_browser.py \
  --database data/benchmarks/my-run/scale-100000.sqlite \
  --output data/benchmarks/my-run/browser-100000.json
```

省略 `--keep-databases` 时规模库用完即删除，只保留报告。支持 `--cases` 选择场景、`--strategy baseline/current/both` 及受限范围的重复次数。旧 `scripts/benchmark.py` 的 2000 人服务层观察保留，与本报告的方法不同，不直接混合数字。

运行 `bash scripts/check.sh` 进行功能回归；普通回归跳过规模浏览器观察，规模浏览器需显式执行，不会默认生成大库。未来仍需真实字段契约、真实分布、MySQL／NebulaGraph 执行计划、部署资源、并发目标和实际办公设备，再决定生产索引、缓存、预计算与容量。

最终回归：254 项后端测试、18 项常规浏览器测试通过，类型／格式／构建及接口生成通过；1 项规模浏览器常规跳过，另在两档库显式运行均通过。实测后端源码摘要与最终源码一致，详细验收见 [验证记录](../prototype-verification.md)。
