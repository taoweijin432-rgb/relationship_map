# 本机 MySQL 模拟验证记录（v0.9）

日期：2026-11-03。用户确认可使用本地 MySQL，没有可用图数据库，Linux 测试服务器目前无法使用。本轮只接通本机 MySQL 的独立模拟实验库，未安装 NebulaGraph，未接正式数据、现有 Canal 或生产同步。

## 数据、环境与方法

- 本机 macOS ARM64、16 GiB 内存，Python 3.12.14，全部后端依赖在 `backend/.venv`；PyMySQL 1.2.3，由 `backend/uv.lock` 锁定。
- 实际 MySQL 服务端 9.7.1，loopback TCP，InnoDB buffer pool 128 MiB，max_connections 151，服务默认 utf8mb4_0900_ai_ci。实验字符串列显式采用 utf8mb4_0900_bin，核对大小写、尾空格、Unicode 和稳定排序。没有调大全局缓存或改变全局优化器参数。
- 沿用 R01 的同一文件快照：1 万人／53,521 条经历、10 万人／531,013 条经历，均含失效记录，种子 42，基准月份 202611。来源映射分别 10,271／102,703 条；不是将来源条数当成去重人数。
- 分别载入新建 `relationship_lab_20261103_ec6d9495` 和 `relationship_lab_20261103_70f387ea`，不覆盖原库。首次导入观察约 3.66／26.84 秒，包含校验与新库初始化，只有一次观察，不能当作持续导入速率或正式 ETL 结论。
- 每档 21 场景 × SQLite／MySQL × 首次一次＋预热七次，最终共 672 次 API 请求。API 通过 ASGI TestClient 及真实路由序列化，数据库是真实本机 MySQL TCP。该测试没有 HTTP socket 并发，也没有目标 Linux、容器数据库或多副本部署。
- 保存请求耗时、响应大小、业务限制、诊断阶段、SQL 与参数、EXPLAIN FORMAT=JSON 和 EXPLAIN ANALYZE。分析计划会额外执行语句，能影响缓存；首次观测不是清空所有缓存的冷启动。只有 7 个预热样本，P95 供定位，不作 SLA。
- 原始记录中的后端源码摘要均为 `30370b5766657741a6fcc5d1a973e29ec6261eb930f63f4fb97d486f02bae1a0`，采集结束后核对一致。嵌套阶段不能相加，SQLite VM 步数不对应 MySQL 扫描行数。

## 接入与查询正确性

新增共享 `read_model.py`、`SQLRepository` 和 `SQLPathReader`，原 SQLite 导入名称保持兼容。API、Service、Domain、游标契约和前端接口不重写；连接装配选择具体引擎。MySQL 实验 DDL 有显式字符串长度，导入前验证，超长值直接拒绝，不静默截断或固定为上游规范。

导入只接受 loopback 的实验库，从只读 SQLite 事务先按批校验再按批写入，完整事务成功后发布元数据。既有表拒绝覆盖；坏数据在建表前阻断。API 会话只读，连接池 5、无溢出、等待 3 秒；普通 SELECT 服务端上限 3000 毫秒。路径按剩余执行预算设置 MAX_EXECUTION_TIME，退出移除监听并回滚，错误 3024 才转换为 time_limit，断连和存储故障保留错误语义。

最终两档均无接口错误、计划执行错误、外部进程超时或已核对的语义差异。每档 19 场景可比较完整响应；热门和长履历路径按预算截断，分别比较已返回链证据并保留 search_complete／truncated 等状态，不将部分结果一致解释为全集证明。

专项 107 项通过：其中 6 项为离线目标约束／错误分类，101 项实际访问 MySQL。包括人工输入与预期人物／证据、跨年与月份窗口、来源和同条经历约束、独立 500 人全部分页及候选集合、大小写／尾空格／重音／通配符／反斜杠／Emoji、只读事务、真实语句超时后连接回收、坏快照不建表、原快照不变、失效／实体纠正／上游人物映射和重启后的旧游标拒绝。独立基准不调用生产查询或时间计算函数。

## 实际发现的计划问题与调整

初始实现的原始记录保留于 [1 万人初始报告](mysql-initial-10000.json) 和 [10 万人初始报告](mysql-initial-100000.json)。MySQL 将部分关联 EXISTS 改写为半连接物化、去重、全量排序；10 万人长履历人物查询触发 3 秒上限，API 明确返回 503。长履历路径在 1500 毫秒执行预算附近停止，只保留已核实直接证据，没有将未查完的中间人物报告成无路径。

以初始 1 万人长履历关系计划为例，参考侧约 98 条有日期的工作经历在热门公司反复展开，产生约 47 万条中间结果，查询预热 P50 约 1296 毫秒。仅使用外层 LIMIT，不能限制这种内部展开工作。

调整后，先探测最多 513 条关联事实；大于 512 时对子查询使用 NO_SEMIJOIN 提示，使外层按稳定人物 ID 扫描、逐人判断 EXISTS，稀疏关系保留普通计划。事实资格、同期窗口、来源、排序和预算没有改变，没有加缓存或预计算全库人物对。提示作用于语句块，不修改全局 optimizer_switch。阈值和提示需在目标版本与真实分布重评，原理参考 [MySQL 官方子查询提示](https://dev.mysql.com/doc/refman/9.7/en/optimizer-hints.html#optimizer-hints-subquery)。

最终计划确认依赖子查询，并在该场景获取 21 位列表人物后结束；10 万人长履历关系预热 P50／P95 为 27.711／29.101 毫秒。长履历路径为 38.183／45.630 毫秒，返回 10 条已核实间接链，仍标明 candidate_limit、path_limit、evidence_limit；没有提高业务预算。

MySQL 没有普遍快于 SQLite。10 万热门实体筛选约 0.11–0.20 秒、深游标 P50 约 151 毫秒、实时元数据计数约 260 毫秒，后续需继续检查查询形状、索引和统计时机。名称定位当前用正则保持原 ASCII 匹配语义，未命中查询 10 万数据 P50 36.169 毫秒，索引效率与正式检索语义还需评估。

完整两人对比仍产生 13,804 条证据、18,250,926 字节；本轮没有分页或裁剪。更换存储不能解决证据组合与传输量，其极端浏览器渲染仍未测量。

最终原始记录：[1 万人](mysql-10000.json)、[10 万人](mysql-100000.json)。每档源 SQLite 文件、默认演示文件和 MySQL 逻辑内容摘要均保持不变。对照的 SQLite 与 MySQL 在同一本机顺序运行，不具有相同驱动、缓存和事务实现，不能据此外推生产组件的相对性能。
