# 人物关系入图预计算验证

2026-11-06 ｜模型 uuid-relations-v2 ｜本机 NebulaGraph 3.8.0／SDK 3.8.3／backend/.venv

用户明确要求在入库阶段计算并保存人物关系。本轮在新图空间验证此流程，现有 API／前端服务、MySQL、旧图、清单和账号均未改变；没有 Supabase 调用。不是把原有“仅事实层”的检查复用为本轮结论。

## 执行与结果

入口：`backend/.venv/bin/python scripts/verify_person_relation_ddl.py --output <新文件.json>`。脚本只接受固定样例与 DDL，随机创建两个 relationship_lab_ddl_ 空间，各自构建完成后只清理本次空间，不提供通用图写入或任意目标配置。没有生产发布功能。

原始记录：[首次演练](data-sources/person-relations-v2-native.json)、[增加完整对账后的最终演练](data-sources/person-relations-v2-native-final.json)。人工基准为 [完整预期样例](examples/person-relations-expected.json)，单独列出修正前后全部证据，未从查询输出生成或覆盖。

每个空间先写 6 位虚构人物、2 家公司、1 所学校、1 个专业和经历边。nGQL 从同一实体的事实边计算候选人物、证据对和同期交集；Python 只编排、分配快照局部 Rank 并写入，不调用 Python overlap／Domain 或 SQL 计算人物关系。

“14 条／10 条”是多重证据边数量，不是不同人物对数量或关系强度。same_company 包括同期及非同期，company_overlap 是其中有可靠同期依据的子集。

两个快照分别验证：

- 预算设为 1 时，图计算返回超预算即中止，尚未调用人物边写入，不将部分结果发布为完整图。
- 所有生成证据与人工 before／after 完整列表一致；写入后从六个已知人物 VID 全部回读，完整键、Rank 和属性与写入一致。
- 重复任职保留两个证据；移除 7001 后，另一条 7002 仍能保留同公司关系。
- 反向从人物乙读取同期边，left／right 仍指存储方向的甲／乙；交集为 202101—202212。修正后该同期边消失。
- 从人物边直接查询得到甲的三位同公司人物，未知时间不被误删。
- 一位中间人物查询只沿两条 same_company，甲经乙连接戊。
- 没有教育时间仍有甲和戊的同校边，事实引用 8001／8002。

最终报告 status=passed，两次 projection.dropped 均为 true；基础与扩展 DDL 及人工样例摘要在报告中留存。DDL 的可空性／类型也实际 DESCRIBE 回读，三种关系属性均无默认值。

## 结论边界

本轮是小样例图内计算和持久化验证，尚未写生产预计算构建器、分布式调度或增量 Worker；样例一次读写不代表可用于大规模。LIMIT 只限制返回量，不是图服务端扫描预算。没有访问 MySQL，因此两个事实 Rank 到真实 SQL 来源的回查和成对 SQL／图发布仍需下一轮验证。

没有生成 ready 控制节点或可激活清单，没有切换旧 API；既有界面仍为 v0.16。人物来源过滤、复杂窗口、阈值、分页、导出、故障恢复、跨月重算及生产容量仍需在新模型接入时回归。小样例预计算成功不能推出热门实体全量人物边可承受。

修正 B 使用独立图空间，不更新 A；测试脚本为构造 B 样例而删除的事实只发生在尚未发布的新临时空间。生产修正仍按新空间完整重建和停服切换，不声称在线旧边级联清理已实现。
