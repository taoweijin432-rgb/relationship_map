## 对当前代码与Demo的影响

当前UUID模式反射12张冻结模拟表，暂未读取名称映射表。因此仅名称映射表改名，对当前12表Demo的直接查询影响有限，但正式15表来源适配和字段说明必须按最终名称更新。

实体BIGINT和移除is_deleted则会直接阻断当前适配。uuid_source.py的mock_schema把实体id及standard_entity_id定义为String(36)，query_tables以is_deleted过滤实体，projection_records使用UUID(id)并直接读取is_deleted。当前图VID为e:<UUID>。

在现有虚构冻结内容的内存副本中，独立替换一项后实际调用projection_records，结果如下。

| 离线输入 | 实际结果 |
| --- | --- |
| 既有冻结虚构来源 | 生成78个业务节点、178条事实 |
| 仅将首个公司实体id改为整数1 | AttributeError，当前UUID解析无法处理整数输入 |
| 保持旧UUID，仅移除首个公司is_deleted | KeyError，当前代码直接访问该字段 |

这些是当前适配器的离线输入探测，没有连接数据库、构建图、切换服务或测试完整新版接入。它们说明新版表不能直接套用当前代码，同时保留既有Demo的有效输入基准。

## 采用新版后的调整范围

1. 按已确认的上游表名、11处ID类型变化及5处删列更新来源契约和字段对应。名称映射失效由同步程序实际清理，CDC消费DELETE旧值或按权威完整快照做差分。
2. 调整SQL表反射后的查询、投影预检和模拟建表。实体有效性需要使用实际存在的字段与已确认状态规则，名称映射不虚构is_deleted。
3. 数字来源采用实体类型命名空间。三张BIGINT表可能各自出现id=1，建议内部实体键company:1／school:1／major:1及图VID e:company:1等。该建议尚待实现并绑定新模型版本，不能按名称推断旧UUID对应新数字ID。
4. 按新身份与字段生成独立SQL／图版本，核对事实Rank、旧新实体引用、证据、列表、路径、专题、对比、导出及游标版本。人物关系继续入图预计算，SQL继续展示姓名。
5. 未来CDC配置相应更新表白名单、主键与行镜像解释。DDL／身份契约改变需要受控重建基线，当前仅检测DML的发布标记不承担DDL兼容性判断。

纯显示字段改名通常可以集中在SQL适配层处理。当前文档同时包含实体身份及删除语义变化，迁移范围需要按上述实际差异评估。三张本项目更新控制表rq_cdc_checkpoint／rq_cdc_event／rq_projection_batch的职责仍适用，具体来源身份、CDC配置及模型版本应绑定新契约。

## 文档内部需核实的位置

- 共用管理字段正文仍写6个，实际表格只有5个。按实际行展开，公司12列、学校13列、专业9列、名称映射11列、公司关系10列、同步批次10列、事实映射11列，合计76列；章节中多个总数仍沿用旧值。
- 实体有效性说明仍提“删除标记和核验状态”，但实体共用表未列is_deleted。名称映射则明确采用同步程序清理失效记录，两者不能混用。
- 表9写人物关系“查询时计算”，与用户已确认的入图阶段预计算及当前实现冲突。本次字段核对不以该表撤销已确认关系规则。
- 仍有graph_conpany、work_expertience等拼写，以及实体表短名残留，不直接将这些文字当作MySQL真实物理名称。

## 本轮决定

已登记新文档、离线兼容性结果及用户采用确认。新目标为BIGINT来源及新版删除规则，映射v5.0保留为UUID历史实现依据。姓名只回SQL、同条经历及图内预计算关系继续执行；表9查询时计算的描述不纳入本次字段确认。当前交付说明影响与迁移设计，完整新版SQL／图集成仍待实现和独立验证。
